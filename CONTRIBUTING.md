# Contributing

This document establishes the engineering rules for this project. These rules exist to maintain the integrity, reproducibility, and clarity of a research-grade codebase.

## Commit Discipline

- **Small, focused commits.** Each commit should represent a single, coherent change. Do not bundle unrelated changes in one commit.
- **Reproducible changes.** Every commit to `src/`, `tests/`, `configs/`, `scripts/`, or `research/experiments/` must leave the repository in a state where the relevant functionality or experiment can be reproduced from scratch.
- **Meaningful commit messages.** Use the conventional commit format: `type(scope): description`. Valid types: `feat`, `fix`, `chore`, `docs`, `test`, `refactor`, `experiment`, `research`. The description must be specific enough that a reader can understand the change without reading the diff. Do not use vague messages such as "update", "fix stuff", or "changes".

## Code Quality

- **Tests for non-trivial implementation.** Any non-trivial function or module added to `src/` must have corresponding tests in `tests/`. Trivial utility functions may be exempt if the rationale is documented.
- **No unexplained generated files.** Do not commit files generated by LLMs, tools, or scripts without documenting exactly what generated them, why, and confirming their correctness.
- **No speculative abstractions.** Do not create base classes, interfaces, plugin systems, or generic utilities unless a specific, immediate use case requires them.

## Dependencies

- **No unnecessary dependencies.** A dependency is added only when it provides a specific capability that cannot be reasonably implemented from existing dependencies without significant cost. The justification must be documented in a commit message or pull request description.
- **No framework-first thinking.** Do not add a framework because it is popular or might be useful later. Add it when you have a concrete requirement it satisfies.
- **Development dependencies are separate.** Runtime dependencies and development/test dependencies must be clearly separated in `pyproject.toml`.

## Security

- **No secrets under any circumstances.** API keys, credentials, tokens, passwords, and connection strings must never be committed to this repository. Use environment variables. If a secret is accidentally committed, rotate it immediately and rewrite history to remove it.
- **No personal data.** Do not commit datasets or outputs that contain personal identifiable information.

## Research and Experimentation

- **Every major implementation must have a justification.** Code added to `src/` must have a clear relationship to an identified project requirement, research question, experiment, or reliability problem documented in `research/`.
- **No architecture changes without a reason.** Structural changes to the repository (new top-level directories, changes to the package structure, new configuration systems) require a clear engineering or research rationale documented before or alongside the change.
- **Experiment definitions before execution.** An experiment in `research/experiments/` must have its definition and design documented before results are added. Do not add results without a corresponding definition.

## Documentation

- **Source code must be readable without documentation.** Use clear, descriptive names. Add docstrings to public functions and modules. Comments should explain why, not what.
- **Keep README files current.** If you add a new directory, script, or major component, update the relevant README.

## Style

- Python code follows the formatting and linting rules configured in `pyproject.toml`.
- No emojis in source code, comments, commit messages, documentation, configuration, or any repository text.
- Use clear, professional technical language throughout.
